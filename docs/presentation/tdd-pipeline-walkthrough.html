What it is

A plugin that runs your coding agent as a test-first pipeline

tdd adds eight slash commands to Claude Code or Cursor. You describe the work in one line; the pipeline plans it, writes tests before code, implements, reviews and opens a pull request.

/tdd:plan "validate input types on add", then answer its questions and confirm the spec
/tdd:review TASK-1, then /tdd:task TASK-1 to start the work

Shortcut: /tdd:task "validate input types on add" runs plan and review in one go, with a single grouped question, then stops at the same gate. Either way, the project needs a test command that runs and a conventions file; init sets up both.

This is the one-minute version. The full path uses one ID throughout: plan writes TASK-1.md, review critiques it, and task TASK-1 reuses that spec instead of drafting another; task still reviews it inline before the gate. For small, clear work, task with a description does both steps itself.

Why it was created

Coding agents write plausible code. Plausible is not the same as correct.

Tests written after the code confirm the code

An agent that implements first writes tests describing what it built, not what was asked. The suite goes green and proves nothing.

An agent grading its own work passes it

The context that made a mistake is the worst place to find it. Self-review in the same session repeats the same assumptions.

Plans rest on guesses about your code

“Extend the existing endpoint” or “the API returns X”, never checked, turns into a whole branch built on a wrong assumption.

State kept in a chat dies with the chat

A session that crashes or runs out of context takes its decisions with it, and the next one starts over.

tdd makes these failures structurally hard instead of relying on a careful prompt: tests first, a fresh agent per phase, specs reviewed against the code, and all state in files.
The design goal is not speed. It is making it hard for an agent to produce work that looks right and is not. Each of these four maps to a mechanism on the next slide.

The trade-off. An inline rule is always read; a pointer to a conventions file depends on the agent finding the right section. So execute cites the exact convention lines it applied, code-review checks every citation, and an area with no rule becomes an explicit warning.
This is the central design decision. Everything in the "your project" column is either a config key or a rule in the conventions file, which is how one package works on any stack. Pipeline protocol, such as the spec structure and handoff log format, lives in core/contracts/, so your conventions file holds only facts about your project.

Installation

Install once per machine, then prepare each project with init

Claude Code · plugin marketplace

claude plugin marketplace add dfrnks/agent-plugins
claude plugin install tdd@dfrnks

# verify: should report Skills (8), Agents (5)
claude plugin details tdd@dfrnks

marketplace add takes the GitHub path. install takes the marketplace's own name, dfrnks. The mismatch is intentional.

Adding the marketplace from a local clone path means edits to the clone take effect on the next dispatch, which is useful when you work on the pipeline itself.

Cursor · user-level plugin

git clone https://github.com/dfrnks/agent-plugins.git \
  ~/src/agent-plugins
ln -s ~/src/agent-plugins ~/.cursor/plugins/local/tdd
# then: Developer: Reload Window

Cursor · per project

./install.sh --harness cursor --project /path/to/project

Both can coexist. An adapter prefers a project's own copy of core/, so a project can pin its own revision. Updating is a git pull in the clone.

install.sh refuses --harness claude-code on purpose: symlinked Claude Code adapters would have no CLAUDE_PLUGIN_ROOT and every pointer would dangle.

Before the first run

Permissions: when one is missing, it doesn't look like a permission problem

The plugin root must be readable

Every command reads files under the package's core/, outside your project. Interactive sessions ask once. Headless runs need it passed in:

claude -p "…" --add-dir /path/to/agent-plugins

git add and git commit must be allowed

init and conventions commit what they write, because a worktree only contains committed files. If git is denied, the files get written, the commits don't, and doctor fails on the "tracked in git" rows.

The configured commands must run

If the test phase cannot run commands.test, it reports unverified instead of claiming red, and the run stops as BLOCKED.

The trap on Claude Code: trust the workspace first. In an untrusted workspace, Claude Code ignores the whole permissions.allow list in .claude/settings.json. Commits fail silently and doctor reports "not ready". Open the project interactively once and accept the trust dialog.
Worth reading before the first run rather than after. The untrusted-workspace case costs people the most time.

init

init proposes, you confirm

  1. 1Detect the stack: test runner, linter, base branch, git-ignored dependencies.
  2. 2Propose the config and ask about everything it could not detect: tracker, conventions path, pull requests, how often the full suite runs.
  3. 3Create directories under .tdd-pipeline/ and git-ignore the worktrees directory.
  4. 4Write a worktree setup script if dependencies are git-ignored (a venv, node_modules, a local .env).
  5. 5Derive conventions by handing off to the conventions flow.
  6. 6Verify the result with doctor.
version: 1
project: ledger
tracker:
  type: none            # none | linear | github
  prefix: TASK          # IDs and branch names: TASK-1, TASK-2
commands:
  test: ".venv/bin/python -m pytest -q {target}"
  test_all: ".venv/bin/python -m pytest -q"
  lint: ".venv/bin/python -m ruff check ."
paths:
  tests: [tests]
  specs: .tdd-pipeline/tasks
  worktrees: .tdd-pipeline/worktrees
  conventions: CONVENTIONS.md   # no default
git:
  base_branch: main
  commit_trailer: ""
  worktree_setup: scripts/setup-worktree.sh
pr:
  enabled: true
policy:
  full_suite: on_execute_and_end   # where test_all runs
Nothing reaches disk until you confirm every value. The directory is named for the pipeline, not for a harness, so the same config works on both.

Configuration rules

The pipeline stops on a missing key. It never guesses.

Every phase reads the config at Step 0. It never infers a command or a path from a package manifest or a directory listing: a wrong guess in an unattended run costs a whole branch of invalid work.

Cannot start: `.tdd-pipeline/config.yaml` is missing
key `commands.test`. Add it, or run the init flow
to regenerate the configuration.

Mode-specific keys follow the same rule. tracker.type: linear also needs tracker.team and tracker.states.

paths.conventions has no default

Point it at the file that already holds your rules. Execute and code-review enforce whatever it contains, so an empty file means they enforce nothing.

git.worktree_setup

Rebuilds what git doesn't track inside each fresh worktree. It runs by its own path, so it needs a shebang and the executable bit.

git.commit_trailer: ""

The only trailer any flow may add. Empty means no trailer at all, and no agent attribution lines either.

The fail-fast message names the file and the exact key. That is deliberate: the fix is always one edit.

policy.full_suite

Choose which phases pay for the full suite

The full run, commands.test_all, is usually the biggest cost in a pipeline. The targeted run, commands.test, always gates every Definition of Done item. The policy only decides where the full run also happens.

Valuetestexecuteend
every_phase default●●●
on_execute_and_end recommended—●●
on_execute—●—
on_end——●
nevernowhere: CI is the regression gate

Unset means every_phase

The slowest value, kept as the default so an upgrade never starts verifying less without anyone choosing it. doctor passes the row with a note that says so.

init measures before it asks

It times commands.test on one small module and commands.test_all, and puts both numbers in the question. A 15-minute full run is roughly an hour per task versus fifteen minutes.

on_execute fails earliest, while a fix is cheap; on_end is the only single run that sees what lint autofix changed after approval, and on_execute_and_end keeps both. A monolith whose modules import each other freely wants every_phase. A repo of independent packages wastes most of that run. never is reasonable when someone watches CI, and expensive when the pipeline runs unattended. What commands.test_all means stays the project's call: a monorepo may define it as the packages a change touches.

conventions

Your conventions are what the pipeline enforces, so this is the step to watch

  • Parallel subagents explore seven areas: layering, error handling, naming, auth, data access, tests, formatting.
  • A pattern becomes a rule only when it holds at two or more independent sites. A single instance is reported as an observation.
  • Every rule carries the file:line it was read from.
  • You accept, edit or drop each group. There is no single yes for the whole set.
  • Doctor fails the project if the managed section holds fewer than five rules.

From this repository's own conventions file

<!-- pipeline:conventions:start -->
## Data access

- Stage named paths; never `git add .` or
  `git add -A` (core/flows/conventions.md:128,
  core/phases/end.md:165).
- Commit anything a phase must read; an
  uncommitted file is invisible from inside a
  worktree (core/flows/conventions.md:130).
<!-- pipeline:conventions:end -->

<!-- pipeline:discoveries:start -->
  findings the end phase appends; never regenerated
<!-- pipeline:discoveries:end -->
The managed span is regenerated on each conventions run. The discoveries span is where later tasks add what they learned; a later conventions run can promote them.

Reading a fail

On not ready, doctor names the exact command for the first failure: init, conventions or a direct config edit. It only names a fix that can actually clear the row.

"exists but is not tracked in git"

The file was written but the commit was not. Neither init nor conventions can clear this row. Check the trust dialog and git permissions, then commit the file yourself.

Run doctor after init and whenever something looks off. Every row should be pass or n/a before the first task. On a greenfield project with no tracked source files, the conventions row is n/a with a stated reason; run conventions after the first code lands.

task · the main entry point

Give task an ID or a sentence. Everything before the gate is read-only.

Before the gate · on the base branch

  1. 0Load configuration, fail fast on a missing key.
  2. 1Resolve the item through the tracker and mark it started.
  3. 2Write the spec. Parallel exploration, then one grouped question about scope and constraints, then a draft committed as TASK-1: add spec.
  4. 3Review the spec against the real codebase, fix it in place, and log a ### review entry.
GateStep 4
“proceed”?

After the gate · in a worktree

  1. 5Create the worktree on a branch named exactly TASK-1.
  2. 6Run the pipeline: a subagent dispatches test, execute, code-review, end.
  3. 7Report: task ID, spec path, review outcome, how the gate ended, result, branch, PR URL.
/tdd:task "validate input types on add"
/tdd:task TASK-12      # existing item
/tdd:task #42          # github tracker
Your local checkout never leaves the base branch. Before the gate, the only file written is the spec.

The gate and the spec

Any answer other than “proceed” stops the run and leaves you a reviewed spec

The gate is a hard stop. Declining leaves a reviewed, committed spec and nothing else: no worktree, no dispatch, no tracker change. That is also the plan-only path. Running task TASK-1 later picks up the existing spec and goes straight to review.

Split signals. If the Approach names more than five changes, or the Definition of Done has more than ten items, the task is several tasks. Split it into TASK-1-1.md, TASK-1-2.md, … under a parent index.

The review blocks a spec that says "verify the API before implementing". External schemas and existing data models get checked during planning, not left to the implementing phase.

Spec skeleton

# TASK-1 — Validate input types on add

## Context          why the change is needed
## Approach         files, functions, data sources, by name
## Files to Modify  every file, one note each
## Definition of Done
- [ ] add() raises TypeError for non-numeric input
      (convention: raise, never return None)
- [ ] Test or verification step
## Out of Scope     so no phase drifts into it
## Agent Handoff Log
<!-- phases append findings here -->
Read the spec before answering the gate. The execute phase follows the Definition of Done literally, item by item.

Worktree

Each task gets its own worktree, on a branch named exactly after the task

Local base in sync with the remote

git fetch origin main
git worktree add --no-track \
  .tdd-pipeline/worktrees/TASK-1 -b TASK-1 origin/main

--no-track keeps the task branch from inheriting main as its upstream. Without it, a bare git push would suggest pushing straight onto main.

Local base has unpushed commits, or there's no remote

git worktree add \
  .tdd-pipeline/worktrees/TASK-1 -b TASK-1 main

Unpushed commits often include the config itself. The report names which ref was used.

Then, inside the worktree

  • The orchestrator checks it is not in the main checkout and that the branch equals the task ID.
  • It checks that the spec's handoff log has a review entry.
  • It runs ./scripts/setup-worktree.sh if configured, and stops on a non-zero exit.

Parallel tasks are supported

One worktree per task, under paths.worktrees, which doctor requires to be git-ignored. An existing worktree with uncommitted work stops the run and asks first.

The pipeline never resets your base branch to match the remote. Your checkout stays as you left it. If a project keeps the config or specs out of git, they are mirrored into the worktree and the spec is copied back after each phase.

task-pipeline (sonnet) dispatches each phase, waits for it to return, and reads one field of its report to decide whether the next runs. It never inlines a phase, never pauses mid-run, and never loops back.

The short reports are for the orchestrator. The detail goes into the spec's handoff log, which the next phase reads in its fresh context.

The opus pinning is a deliberate cost decision: those three are the phases where a weaker model produces work that looks right and is not. It can be changed in agents/ frontmatter. Cursor uses whatever model you selected.

Phase: test · red

Red is something the phase observed, not something it assumed

  • Studies existing test patterns, writes a test plan, then writes tests under paths.tests.
  • Runs commands.test. Every new test must fail for the reason it asserts. A typo, import error or broken fixture also shows red, and proves nothing.
  • A test that passes before the implementation is either a regression guard (kept, noted as green by design) or a test that doesn't exercise the change (rewritten).
  • Under policy.full_suite: every_phase, also runs commands.test_all to confirm nothing that already passed broke.
StatusNextMeaning

n/a (nothing testable)executeNothing a command can observe (prose only). Code-review checks the claim.
pass (green)BLOCKEDThe tests describe no new behaviour.

Tests: tests/test_ops.py. 4 tests written.
Status: fail (red). Committed: yes.
Unverified is an environment or permission failure, not a test-design problem. The fix is making the command runnable.

Phase: execute · green

The committed tests are the contract, and execute may not rewrite it

Test protection contract

  • Never modify an existing assertion to make the code pass.
  • Never delete a test.
  • Never weaken a condition: exact match to substring, a dropped edge case, a relaxed mock count.
  • Add new tests for scenarios found while implementing.
Tie-breaker. If a "scaffolding fix" to a test file would change any assertion's expected value, it is not a scaffolding fix. Execute stops and escalates instead of editing.

What else it does

  1. 3Loads conventions and records a ### Conventions Applied block citing each rule used.
  2. 7Verification loop per Definition of Done item, then the full suite unless the policy is on_end or never.
  3. 8Lint gate with commands.lint.
  4. 10Test protection gate: compares test files in the working tree with the test phase's commit.

Stops and asks instead of guessing when

  • a Definition of Done item is impossible as written,
  • two items conflict,
  • the work needs infrastructure outside the task's scope.
If a test looks wrong, execute implements toward the spec and documents the conflict in the handoff log. Code-review decides; execute never silently rewrites.

Phase: code-review

Six review dimensions, three severities, one verdict

DimensionWhat it checks
Spec complianceEach Definition of Done item: satisfied, partial, missing. Undocumented deviations are findings.
ConventionsEach citation in Conventions Applied points at a real rule, and the code follows it.
Security and isolationAuthorization on new entry points, input validation, tenant scoping, no secrets.
Test integrityDiffs every test file against the test phase's commit. Nothing weakened, deleted or re-expected.
Test qualityA test per Definition of Done item, error paths covered, and no production logic that exists only to satisfy a test.
ChecklistSpot-checks execute's Implementation Manifest, and scans paths.review_checklist if set.

Severity

Blocker must be fixed: security hole, cross-account leak, unmet Definition of Done item, weakened test.

Warning should be fixed: uncovered area, minor convention deviation.

Suggestion doesn't affect the verdict.

Verdict: CHANGES_REQUESTED.
Blockers: DoD 2 unmet (float input accepted).
Warnings: none.

One blocker means no approval. CHANGES_REQUESTED stops the pipeline. It does not loop back to execute on its own; a person decides with resume.

Why no automatic loop: each unsupervised execute pass makes changes the rejecting review never saw, so nothing converges toward approval.

Phase: end

end ships only what code-review approved

  1. 1Detect changed areas from the diff.
  2. 2Lint. Re-run commands.test_all if autofix could change behaviour, and always under on_end.
  3. 3Persist discoveries: project facts go to the conventions file's discoveries span; phase quirks go to .tdd-pipeline/memory/<phase>/.
  4. 4Commit and push the branch, staging named paths only.
  5. 5Open the pull request against the base branch. Skipped if pr.enabled: false, there's no remote, or one already exists.
  6. 6Update the tracker to its review state.
  7. 8Cleanup hint: the git worktree remove command, to run only after the PR merges.

Pull request body

Summary of what changed.

Definition of Done copied from the spec, with satisfied items checked.

Lint: clean.

The orchestrator reads only the last line of this report; if it is missing, the run is treated as stopped. A failed tracker update is a stop, not a warning. A board that says in-progress while the code has shipped is exactly what the pipeline is trying to prevent.

Results

Every run ends with one of three results

SHIPPED

The end phase reached its last step. The branch is pushed and the PR is open.

What you do

Review and merge the PR like any other. Remove the worktree afterwards.

STOPPED

  • code-review returned CHANGES_REQUESTED
  • execute stopped or escalated
  • the worktree guard or setup script failed
  • end stopped partway (push, tracker)

What you do

Read the reason and the handoff log, fix the cause, then resume TASK-1.

BLOCKED

  • test reported pass (green)
  • test reported unverified
  • the spec has no review entry

What you do

Make commands.test runnable, run review on the spec, or rethink what the tests should describe.

A non-shipped report always carries a one-line reason, the branch and the worktree path, so you know where to pick up.

BLOCKED means the pipeline could not start meaningful work. STOPPED means it started and something needs a decision.

The handoff log

Phases talk to each other only through the spec's handoff log

Illustrative

### review (2026-09-10)
- Spec named calc.py; add() lives in ledger/ops.py.
  Fixed Files to Modify.

### test (2026-09-10)
- 4 tests in tests/test_ops.py, red on TypeError.
- test_add_ints_unchanged: regression guard,
  green by design.

### execute (2026-09-10)
- Validation in ledger/ops.py; no test file touched.
- Conventions Applied: raise, never return None
  (ledger/io.py:41)

### code-review (2026-09-10)
- Verdict: APPROVED. Blockers: none.

Each phase reads the whole log before it starts and appends one dated entry before it finishes. Entries are never edited. Useful notes are concrete: "changing this identifier breaks six tests", not "be careful".

Where a finding goes

When a finding could go in either the conventions file or the log, the conventions file wins.

This is why resume works: the log records which phases ran and what they concluded, and it is committed with the branch.

resume

resume runs exactly one phase and stops

/tdd:resume TASK-1            # infer the phase from the log
/tdd:resume TASK-1 execute    # or name it

How it picks the phase

  1. 1Find the last test, execute, code-review or end entry, by position in the file.
  2. 2None yet → test.
  3. 3code-review with CHANGES_REQUESTED → execute.
  4. 4end → nothing to resume. It never re-runs end blind.
  5. 5Otherwise → the next phase in order.

A rejected review, fixed

### review
### test
### code-review   CHANGES_REQUESTED
  → resume picks execute
### execute
  → resume picks code-review

Each resume is one deliberate step by a person. After the fix, the next resume runs code-review, so the fix gets reviewed before anything ships.

The branch name is how resume finds a task. It looks up refs/heads/TASK-1. Rename the branch and resume will say there is nothing to resume.
Resume refuses to run any phase, including test, against a spec with no review entry.

Constraints

Four constraints to know before you rely on it

The branch name is the task ID

No feature/ prefix or username. Team branch naming conventions aren't supported yet, and a renamed branch is invisible to resume.

Three agents run on the larger model

test, execute and code-review are pinned to opus; the orchestrator and end use sonnet. A full task runs all five. Change it in the frontmatter under agents/.

It commits on your current branch

init, conventions and the task spec are committed to the base branch, because worktrees only see committed files. Only named paths are staged, so your own uncommitted work stays uncommitted.

It stops rather than degrading

A missing key, an unauthenticated tracker or a suite it can't run each stop the run with the exact fix. Plan for a few stops while you set up a new project.

The validation doc in docs/ records the first end-to-end run against a real project, including what was not verified.

Cheat sheet

Your first task in five minutes

# 1. install (Claude Code)
claude plugin marketplace add dfrnks/agent-plugins
claude plugin install tdd@dfrnks

# 2. bootstrap: confirm the config, review each rule group
/tdd:init

# 3. every row pass or n/a
/tdd:doctor

# 4. optional: design first when the approach isn't settled
/tdd:plan "validate input types on add"
#    → TASK-1, spec at .tdd-pipeline/tasks/TASK-1.md
/tdd:review TASK-1

# 5. run it: task reuses the TASK-1 spec, reviews it inline,
#    stops at the gate (skipped step 4? pass a description)
/tdd:task TASK-1
#    → gate: proceed

# 6. only if something was interrupted or rejected
/tdd:resume TASK-1

Where things live in your project

.tdd-pipeline/config.yamlthe only required file
.tdd-pipeline/tasks/TASK-1.mdspec and handoff log, from plan or task
.tdd-pipeline/worktrees/TASK-1/one per task, git-ignored
.tdd-pipeline/memory/<phase>/phase-workflow learnings
paths.conventionsthe rules that get enforced

On Cursor, the same commands use a dash: /tdd-init, /tdd-plan, /tdd-review, /tdd-task.

Source and docs: github.com/dfrnks/agent-plugins. The README covers permissions, updating and the full config schema.

Step 4 is optional: without it, run task with a description and it writes the spec itself. With it, plan resolves TASK-1 and writes the spec under that ID, and task TASK-1 reuses it instead of drafting another. Suggest people start with a small, well-understood change so they see every phase once before trusting it with something bigger.
